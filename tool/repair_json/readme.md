# 修复 labelme json 的 `imagePath`（与图片文件名对齐）

检查 labelme json 里的 `"imagePath"` 是否等于**那张图片的实际文件名（名字 + 后缀）**，
不一致就改成一致的：

```
plant_ S221-4_20251116ST.json
  ✗ "imagePath": "plant_ S221-4_20251116ST.png"      ← 改前
  ✓ "imagePath": "plant_ S221-4_20251116ST.jpg"      ← 改后（以磁盘上的实际文件名为准）
```

## 为什么会不一致

**labelme 记的是「当初标注时那张图叫什么」**，之后图片被转格式或改名，json 里的值不会跟着变。
这个项目里就是 png → jpg 的批量转换（或
[tool/add_suffix](../add_suffix/add_suffix.py) 改名）留下的：图变成了 `.jpg`，
json 里还写着 `.png`。

## 影响范围

- **不影响本项目的训练/推理**：`imagePath` 只在
  [common/labelme.py](../../common/labelme.py) 的注释里出现过，**没有任何代码读它**。
  配对和统计全靠**文件名**，模型指标不受影响。
- **有影响的是 labelme 本身**：打开 json 时它按 `imagePath` 去找图，后缀对不上就加载失败
  （画布空白 / 报 "cannot load image"），标注没法看也没法改。RootNav 之类同理。

所以：**不急着修数据，但要在 labelme 里继续标注之前必须先修。**

## 用法

在项目根目录下运行：

```
python tool\repair_json\repair_json.py --dir "D:\目标文件夹" --dry-run      # 先预览
python tool\repair_json\repair_json.py --dir "D:\目标文件夹"                # 正式修复
python tool\repair_json\repair_json.py --dir "D:\目标文件夹" -r             # 递归子文件夹
python tool\repair_json\repair_json.py --dir "...\labels\other" --images "...\images"
```

| 参数 | 说明 |
| --- | --- |
| `--dir` | 目标文件夹（**必填**，在里面找 `.json`） |
| `-r` / `--recursive` | 递归子文件夹（默认只看本层） |
| `--images` | 图片所在文件夹；**默认与 json 同目录**。项目 `datasets/root/train/` 那种 `labels/other/` 与 `images/` 分家的布局要指定它 |
| `--dry-run` | 只打印将要改的内容，不写文件 |
| `--force` | 连「名字也不同」的也改（默认只报告，见下） |

**这是就地修改文件的有损操作，请先 `--dry-run` 预览一遍**（同 [tool/repair_rsml](../repair_rsml/repair_rsml.py)）。

修复后会在目标文件夹里生成 `repair_json_log.txt`，逐条记录「相对路径 → 旧值 → 新值」，
需要回滚可以按它手工改回去。

> ⚠️ **日志别留在数据文件夹里**：如果这个文件夹接下来要拿去划数据集
> （[tool/separate_dataset](../separate_dataset/readme.md)），请先把日志挪走 ——
> 划分工具是按「文件夹里所有文件」分组的，一个 `.txt` 会被当成一组文件划进 train/test。

## 判定与处理口径

以「磁盘上实际存在的同名图片」为准，分五种：

| 情况 | 例子 | 处理 |
| --- | --- | --- |
| **后缀不一致** | json `.png` / 实际 `.jpg` | ✅ 自动改 |
| **大小写不一致** | json `.JPG` / 实际 `.jpg` | ✅ 自动改 |
| **缺后缀** | json 只有名字，没后缀 | ✅ 自动补 |
| **名字也不同** | json 指向另一张图 | ⚠️ **只报告，不动**（要改加 `--force`） |
| 本来就是对的 | 逐字符相同 | 报「正常」，不写文件 |

两条刻意的设计：

- **大小写也算不一致**。Windows 上 `x.JPG` 和 `x.jpg` 都打得开，但训练跑在 **Linux 服务器**上，
  那边区分大小写 —— 所以按磁盘上的真实写法对齐。
- **「名字也不同」默认不改**。那多半不是「后缀写错」，而是 **json 配错了图**（标注内容其实
  属于另一株）。悄悄改成旁边那张图的名字，等于把一个真错误盖掉、让它以「已修复」的样子
  混进数据集 —— 这正是最该被看见的情况。所以它只报告、退出码不变，要改得显式加 `--force`。

另外这几种**跳过不猜**：

| 情况 | 为什么 |
| --- | --- |
| 找不到同名图片 | 没有依据，不发明一个名字出来 |
| 同主干有 2 张图（`x.png` 与 `x.jpg` 并存） | 该指向谁无法判断。训练管线（`discover_pairs`）也只认**主干精确相等**，这种情况本来就会出问题，得先把重复件清掉 |
| 缺 `imagePath` 字段 / 值不是字符串 | 只报告。工具不负责往 json 里插新字段（插入位置没有可靠锚点，猜错会破坏文件） |
| json 解析失败 / 编码不是 utf-8 | 跳过并报告，不猜编码 |

## 为什么是文本替换，不是 json 往返

`json.load` → `json.dump` 会把**整个文件重写一遍** —— 缩进、空格、浮点写法
（`317.24999999999994` 这种坐标值）、转义都可能变，`imageData` 里那几 MB 的 base64
也要重新编码。标注数据不该冒这个险。

本工具只在文本层面替换 `"imagePath"` 后面那个**字符串值本身**，其余字节原样保留：

```
改前 326 字节 -> 改后 326 字节（只换了后缀）
抠掉 "imagePath": "…" 的值之后，两份文本**逐字节相同**  ← 实测 6 个用例全部成立
```

值里若原本带目录前缀（`"images/x.png"`），只换文件名部分、**前缀保留**；
值里若有需要转义的字符，写回时用 `json.dumps` 正确转义。

顺带一提：读写都用 `newline=""`，**不做换行转换** —— 否则 Windows 上会把整份文件的
`\n` 悄悄改成 `\r\n`，变成一个巨大的假 diff。

## 边界情况

- **文件名里的空格保留**：`plant_ S221-4_20251116ST` 的值就该带那个空格。
  这一点和 [tool/analysis_datas](../analysis_datas/) 相反 —— 那边按项目约定去空格做**解析**，
  这里要跟文件名**逐字对齐**，所以不能去。
- **一个文件里出现多个 `imagePath`**：全部替换成同一个值（正常文件只有一个）。
- **正则不会串到别的键上**：前面加了否定环视，`originalImagePath` 这类同样以
  `imagePath` 结尾的键不会被误伤；`imageData` 里的 base64 不含引号，也不会被吃进来。
- **幂等**：已经是正确的文件报「正常」，重复运行不产生任何改动。

## 实测（2026-09-17，源数据集 `数据集总表\root` **已跑过一次**）

36 个 json：**20 个不一致**（全部是「后缀不一致」：json 写 `.png`，实际是 `.jpg`），
16 个正常。正常的那 16 个里包含当天新存的 5 个（`S002-3`、`S002-4`、`S003-1`、`S003-2`、
`S003-3`）—— 重新导出时 labelme 记的是 `.jpg`，本来就是对的。

已执行修复，当场核验：

```
未改动 16 个 | 只改了 imagePath 值 20 个 | 夹带其它改动 0 个
复核：36 个 json 的 imagePath 与磁盘文件名 全部一致
```

（`repair_json_log.txt` 已挪到源文件夹**外面**的 `数据集总表\` 下，免得被划数据集时卷进去。）
